# gear-algorithm (experimental)

This is the lightweight Python author package for Gear's experimental Campaign runtime. It has no Torch, CUDA, Optuna or training dependencies. It requires Python 3.11+; the current Node host also checks for POSIX `fcntl` in that interpreter. The Node/TypeScript Gear host and its CLI are installed separately; installing this wheel does not install Node, Gear, Hitch or a model provider. See the [author guide](../../docs/algorithm-authoring.zh-CN.md) for the three supported author paths and host ownership.

An algorithm exports an object with `describe()`, `initialize(context)` and `reduce(context)`. `describe()` returns `AlgorithmManifest` with state/config/binding schemas. `@task(name, kind=...)` names a pure input builder that emits an `OperationIntent`; `@decision(name)` names a pure decision function; `parallel()` gives a stable key order. Return `AlgorithmDecision` or use `advance()`. Side effects belong in providers, and Gear resumes at step boundaries rather than inside a Python stack frame.

For a fixed sequence, `define_workflow(id=..., config_schema=..., binding_schema=..., business_state_schema=..., initial_state=..., steps=[WorkflowStep(name, plan, join), ...])` owns the JSON step cursor. Each `plan` emits named Gear operations; its `join` receives their committed outcomes and returns `(next_business_state, optional_binding_transition)`. The helper validates the business state after every join and never keeps an uncommitted Python call stack.

`gear_algorithm.recipes.rho`, `.ahe`, and `.evo` contain one Python scientific implementation each; the TypeScript `rsi-gear/algorithm/recipes` exports are location/operation declarations, not duplicate algorithms. RHO selects a managed coreset, measures a fixed baseline repeatedly, proposes harness directories, and accepts only positive unlabeled paired self-preference. AHE measures the executed revision before attributing and proposing another, keeping its best measured revision distinct from pending work. Evo consumes sealed TaskView batches with one frozen skill binding per batch and commits the cursor with a skill update. The public `rsi-gear/algorithm/harness` entry offers `createConfiguredFreshHostProfile` for an administrator to assemble the physical Hitch/DSH/Git providers once. Its Evo path checks exact Skill library members, materializes a Git overlay, and verifies the executed commit and receipt. The Python recipe author still writes only Python science policy; see `examples/algorithms/{rho,ahe,evo}`.

RHO/AHE page through authorized `evidence.query`, read selected content through `evidence.read`, and give bodies plus read receipts to difficulty/attribution roles. A historical ExperienceView can authorize `overview`, `task-report`, and real `trace-chunk` projections; the fresh compiled-seed source authorizes only `overview` and `task-report` and freezes `historyTraceAvailable=false`. It never manufactures old trajectories. New rollout traces are read separately through the exact completed producer evidence/receipt pair. The host, not the recipe, resolves these grants. `operationLimits`, keyed by operation kind, reserves Campaign budget before each emitted operation; each installed provider's metered dimensions must have matching budget sources. For example, `{"evidence.query":{"evidence.items":1,"evidence.bytes":4096},"execution.rollout":{"rollout.trials":1}}` reserves these dimensions for those kinds. No reservation is inferred for a missing key. The default host freezes these limits and seals real DSH/model/tool and Hitch usage receipts. `model.tokens` is stop accounting, not a guaranteed hard cap. These limits and the provider catalog are frozen across resume.

The optional `gear_algorithm.adapters.optuna` module pins Optuna 4.9.0 when constructed. `OptunaAskProvider` and `OptunaTellProvider` run each step on a separate trusted in-memory study copy, seal an HMAC-authenticated checkpoint artifact, and return JSON refs. The provider alone decodes pickle after authentication. The checkpoint currently has a 2 MiB bound to fit the worker artifact frame. `gear_algorithm.recipes.optuna_search` wraps `ask → external Gear evaluation → tell`; the evaluation kind also uses `operationLimits` when its provider meters usage. `examples/algorithms/optuna` is a runnable two-trial CPU example that reserves and reports one `evaluation.calls` per trial. Optuna is never a wheel dependency, and missing/mismatched Optuna must fail `check` for that adapter.

A policy hook uses `@component(id=..., input_schema=..., output_schema=..., scope=...)` on one function. The loader supplies implementation and environment digests from observed files, interpreter and imported modules. Hook input/output schemas and scope must match the recipe's declared slot. `policy.decide` is a normal durable operation: a committed choice is reused on resume; a started call without a sealed result stays `unknown` and needs reconciliation.

A Python provider implements `describe/preflight/submit/inspect/cancel/collect`. `ProviderManifest` declares one operation kind, schemas, metered dimensions, optional enforceable hard dimensions and trusted-local/external execution. `ArtifactClient` seals/reads content through a host-authorized bridge; it does not require a private TypeScript registry. `DurableLocalProvider` supplies fsynced started/result/cancelled records for synchronous deterministic local work. A cancelled-before-start operation cannot later be submitted; its confirmed release includes a zero final usage receipt. Metered subclasses must implement `usage_receipt()` with actual final cumulative values and pass a `metering_source` matching the Campaign budget. A started operation without a sealed completion remains unknown. This helper deliberately does not implement unknown external sends, GPU budgets or background jobs. For an external system, implement stable idempotency and inspect against that system and report real usage receipts. `gear_algorithm.testkit` checks duplicate submit, input drift, dropped reply and restart inspection.

The worker uses an authenticated, length-limited TCP connection bound to `127.0.0.1`; stdout and stderr are logs. A single frame is limited to 4 MiB, including base64 artifact transfer. Transfer large checkpoints through a provider's own validated artifact path. The worker runs trusted local code and is not an OS sandbox. The wire accepts only finite, safe-range JSON values and refs, never pickle or Python objects. The TS host computes Gear digests. The installed wheel does not set up the Node host or authorize model/data destinations.

Python `interpreter` is an absolute path, a path relative to `gear.algorithm.json`, or a command resolved from `PATH`. Python `module` is a dotted import or a `.py` path; relative `.py` paths are resolved from the configuration directory. `export` is one public Python identifier. The project source closure includes Python/ESM/JSON/TOML/YAML/lock and `requirements*.txt` files under that directory, excluding `.gear`, virtual environments, `node_modules` and caches. Additional data files used by an algorithm must be listed in the entry's `resources`; those files are hashed. Installed Python modules loaded when the export is imported are also hashed. Load scientific dependencies at import time so `check` can catch missing packages and record them in the identity. `check` imports trusted modules and does not submit Campaign operations; host model registration may still query service metadata.

Start from `examples/algorithms/python-toy` or run `gear-refine algorithm init DIRECTORY python`. From the Gear repository, build and install the local wheel into the selected POSIX interpreter (the wheel is not assumed to be on PyPI):

```sh
python3.11 -m pip wheel --no-deps -w dist packages/python-sdk
python3.11 -m pip install --no-deps dist/gear_algorithm-*.whl
```

Then use `gear-refine algorithm check|run|resume gear.algorithm.json` (or `node lib/algorithm/cli.js check|run|resume ...` from a built checkout). Even a TypeScript-only Campaign currently needs POSIX Python 3 with `fcntl` for the Node host's writer lock; `GEAR_ALGORITHM_LOCK_PYTHON` can select it. `check` imports trusted author code and host configuration; it is not a sandbox or a live model test. A production model adapter's registration or `resolveModelInfo` can query service metadata, so `check` is not inherently offline. `npm run test:algorithm:package` verifies an installed npm tarball and isolated wheel with toy Campaigns; its external recorded host fixture also runs the installed CLI's physical-profile `check` against the installed wheel without submitting a model/Hitch job. Full RHO/AHE/Evo recipes have offline Git/DSH/recorded-Hitch tests, not paid-model, GPU or human-author validation. Public contracts remain experimental.

`algorithm init` writes a new globally unique `campaignId` and a matching `.gear` state path. Preserve that ID and the frozen configuration when resuming. If you construct `CampaignSpec` directly, assign each new campaign a globally unique ID; external provider idempotency keys derive from it.
