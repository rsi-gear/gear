# gear-algorithm (experimental)

This is the lightweight Python author package for Gear's experimental Campaign runtime. It has no Torch, CUDA, Optuna or training dependencies. The Node/TypeScript Gear host and its CLI are installed separately; installing this wheel does not install that host.

An algorithm exports an object with `describe()`, `initialize(context)` and `reduce(context)`. `describe()` returns `AlgorithmManifest` with state/config/binding schemas. `@task(name, kind=...)` names a pure input builder that emits an `OperationIntent`; `@decision(name)` names a pure decision function; `parallel()` gives a stable key order. Return `AlgorithmDecision` or use `advance()`. Side effects belong in providers, and Gear resumes at step boundaries rather than inside a Python stack frame.

For a fixed sequence, `define_workflow(id=..., config_schema=..., binding_schema=..., business_state_schema=..., initial_state=..., steps=[WorkflowStep(name, plan, join), ...])` owns the JSON step cursor. Each `plan` emits named Gear operations; its `join` receives their committed outcomes and returns `(next_business_state, optional_binding_transition)`. The helper validates the business state after every join and never keeps an uncommitted Python call stack.

`gear_algorithm.recipes.rho`, `.ahe`, and `.evo` contain one Python scientific implementation each. RHO selects a historical coreset from managed evidence, measures a fixed baseline repeatedly, proposes harness directories, and accepts only positive unlabeled paired self-preference. AHE measures the executed revision before attributing and proposing another, keeping its best measured revision distinct from pending work. Evo consumes sealed TaskView batches with one frozen skill binding per batch and commits the cursor with a skill update. The host must provide the physical role, workspace-edit, rollout and feedback operations. The current CLI lacks a ready-made host-profile factory for those capabilities, and the Hitch bridge does not yet verify dynamic Evo skill injection; see `examples/algorithms/{rho,ahe,evo}` for honest author templates.

RHO/AHE host profiles must authorize and seal `overview`, `task-report`, and `trace-chunk` projections in the ExperienceView. The recipes page through `evidence.query`, read the selected content through `evidence.read`, and give the resulting bodies and read receipts to difficulty/attribution roles. The Campaign config may include `operationLimits`, keyed by operation kind. For example, `{"evidence.query":{"evidence.items":1,"evidence.bytes":4096},"execution.rollout":{"rollout.trials":1}}` reserves these amounts in each emitted operation. Each kind's keys must exactly match the assembled provider's `meteredDimensions`; the dimensions must exist in the Campaign budget with the provider's receipt source. No reservation is inferred for a missing key, so a metered provider fails admission instead of silently running unaccounted work. For DSH roles, reserve `model.requests` and `model.tokens` only when the host's actual provider reports those dimensions; the token amount must cover that role's enforced generation cap. These limits and the provider catalog are frozen across resume.

The optional `gear_algorithm.adapters.optuna` module pins Optuna 4.9.0 when constructed. `OptunaAskProvider` and `OptunaTellProvider` run each step on a separate trusted in-memory study copy, seal an HMAC-authenticated checkpoint artifact, and return JSON refs. The provider alone decodes pickle after authentication. The checkpoint currently has a 2 MiB bound to fit the worker artifact frame. `gear_algorithm.recipes.optuna_search` wraps `ask → external Gear evaluation → tell`; the evaluation kind also uses `operationLimits` when its provider meters usage. `examples/algorithms/optuna` is a runnable two-trial CPU example that reserves and reports one `evaluation.calls` per trial. Optuna is never a wheel dependency, and missing/mismatched Optuna must fail `check` for that adapter.

A policy hook uses `@component(id=..., input_schema=..., output_schema=..., scope=...)` on one function. The loader supplies implementation and environment digests from observed files, interpreter and imported modules. Hook input/output schemas and scope must match the recipe's declared slot. `policy.decide` is a normal durable operation: a committed choice is reused on resume; a started call without a sealed result stays `unknown` and needs reconciliation.

A Python provider implements `describe/preflight/submit/inspect/cancel/collect`. `ProviderManifest` declares one operation kind, schemas, metered dimensions, optional enforceable hard dimensions and trusted-local/external execution. `ArtifactClient` seals/reads content through a host-authorized bridge; it does not require a private TypeScript registry. `DurableLocalProvider` supplies fsynced started/result/cancelled records for synchronous deterministic local work. A cancelled-before-start operation cannot later be submitted; its confirmed release includes a zero final usage receipt. Metered subclasses must implement `usage_receipt()` with actual final cumulative values and pass a `metering_source` matching the Campaign budget. A started operation without a sealed completion remains unknown. This helper deliberately does not implement unknown external sends, GPU budgets or background jobs. For an external system, implement stable idempotency and inspect against that system and report real usage receipts. `gear_algorithm.testkit` checks duplicate submit, input drift, dropped reply and restart inspection.

The worker uses an authenticated, length-limited TCP connection bound to `127.0.0.1`; stdout and stderr are logs. A single frame is limited to 4 MiB, including base64 artifact transfer. Transfer large checkpoints through a provider's own validated artifact path. The worker runs trusted local code and is not an OS sandbox. The wire accepts only finite, safe-range JSON values and refs, never pickle or Python objects. The TS host computes Gear digests.

Python `interpreter` is an absolute path, a path relative to `gear.algorithm.json`, or a command resolved from `PATH`. Python `module` is a dotted import or a `.py` path; relative `.py` paths are resolved from the configuration directory. `export` is one public Python identifier. The project source closure includes Python/ESM/JSON/TOML/YAML/lock and `requirements*.txt` files under that directory, excluding `.gear`, virtual environments, `node_modules` and caches. Additional data files used by an algorithm must be listed in the entry's `resources`; those files are hashed. Installed Python modules loaded when the export is imported are also hashed. Load scientific dependencies at import time so `check` can catch missing packages and record them in the identity. `check` imports trusted modules but never submits an operation or calls a paid model.

Start from `examples/algorithms/python-toy` or run `algorithm init DIRECTORY python`. Build the wheel with `python -m pip wheel --no-deps -w dist packages/python-sdk`, install it into the selected interpreter, then use the host's experimental `node lib/algorithm/cli.js check|run|resume gear.algorithm.json` entry. Public contracts remain experimental pending independent provider and real training acceptance.

`algorithm init` writes a new globally unique `campaignId` and a matching `.gear` state path. Preserve that ID and the frozen configuration when resuming. If you construct `CampaignSpec` directly, assign each new campaign a globally unique ID; external provider idempotency keys derive from it.
