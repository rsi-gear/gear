# A1 `author.measurement` narrow contract (implementation slice)

`author.measurement` is a trusted-local, zero-meter operation. Its author-visible input is only `{subject, selection, producerOperationIds}`. It never accepts metrics, evidence refs, receipts, evaluator refs, or a comparison key from the author. Its result is `EvaluationV1`; only a complete result has `metrics`, `measurementRef`, and `comparisonKey`.

The real host must inject a frozen profile and a **read-only** committed-operation resolver. The profile binds the campaign, execution-profile digest, permitted signed TaskView roots, repeat count, expected rollout adapter digest and physical Hitch digest, sampling/environment digests, evaluator/rubric/environment/sampling/budget/metric-schema CAS refs, and the resolved raw metric contract. The metric-schema artifact must name the metric contract digest, so a change in extraction semantics changes the existing `measurementComparisonKey`. The host must derive those refs from the resolved run lock and compiled dataset, not author input. In particular, `evaluatorRef` and `rubricRef` are host declarations of the actual physical scoring contract; the current Hitch evidence does not directly name those CAS refs. Before real host wiring, admission must prove this mapping to the locked Hitch config / benchmark metric registry. If that mapping cannot be proven, add only those explicit digests to the physical evidence/receipt; do not infer them from a score.

The resolver must read **one** hash-verified Campaign journal snapshot for the batch of named operation IDs and the immutable physical Hitch producer journals, without calling submit/inspect/collect or starting work. For each operation ID it returns the kernel-committed envelope, status/outcome, the physical completion, and its **exact saved EvaluationRequest**, request digest, and submitted identity. The measurement provider verifies `digestJson(request)`, derives `conditionId` from the request condition, compares request dataset/ref/commit/repetitions with evidence, and checks the remaining condition fields against the frozen profile. It also compares both completion identities, the byte-equal committed outcome, adapter and physical implementation digests, bound subject/actual slots, receipt/evidence refs, task/repeat slot, submitted identity, and unique evalId **and runId** (a new attempt does not license reusing one runId). A kernel operation that has no committed completion is rejected as a named source even if the physical provider journal has a result. Current Campaign state persists the committed **outcome**, not the full completion, so the host resolver has to pair it with the saved provider completion and verify equality. Current Hitch producer journals save only `requestDigest`; the new neutral v2 producer must atomically save the exact request too. Old journals without it are not accepted by this v2 measurement path. A standalone physical journal or caller-supplied receipt is insufficient.

One selected signed view is used for all subject evaluations. The provider verifies the selection exactly matches its signed TaskView, and that every producer uses that same view. Coverage is the Cartesian product of selected task IDs and frozen repeat indices `0..repeatCount-1`. An omitted slot, a committed business failure, or a physically invalid trial stays visible as `incomplete`/`invalid` with per-trial status and no aggregate. A **named** producer ID that is pending or absent is rejected before measurement commitment: otherwise its later completion could change the original key's outcome. Complete trials use the frozen `RawMetricContract` and existing raw metric extractor/aggregator. The current Hitch `conditionId` and `effectiveConfigDigest` can vary with task projection, so they are checked against saved physical request/submission identity per operation, not against one run-wide constant. Cold recomputation with the same operation envelope and committed producer snapshots yields identical CAS bytes and the same `EvaluationV1`.

This initial physical slice requires an exact `harness` binding and rejects Skill overlays until their separate overlay receipt is verified. It does not wire the author `ctx.evaluate` composite, Hitch submission, CLI, or package exports. The future composite must obtain producer operation IDs from host-authored v2 replay history/tracked calls, including terminal failures; the author cannot invent them from outcomes. Those need separate host integration and end-to-end validation.
