## 确认的问题

1. 单题导入进入 `nativePhaseDescriptor` 和评分证据保存时，各自调用完整数据集校验。普通任务即使没有 native descriptor，也先扫描全部题目文件，再返回。100 题逐题导入会反复读取其他 99 题的内容；缺失 bundle 的诊断导入也涉及评分校验。
2. `EvalProgressV1` 原来只接受 `running`，正常终结函数写出 `result.json` 后没有同步进度终态。因此交接包记录的 `progress=running` 与 `result=cancelled` 在代码上确实可能发生。
3. 审计发现附带的恢复风险：Gear 原来优先读取 active control，再检查持久化结果。Hitch 先写结果再更新 control，短暂滞后或崩溃后会让 Gear 将已有最终结果判断成运行中。交接包仅证明 progress 滞后，未证明历史事件中 control 也滞后；这里作为相同边界的防护修复。

交接包中的“19 题隔离回放从约 713 秒降到约 4.6 秒”属于包内实验记录。本次没有获取原始私有 19 题 fixture，也没有重新运行正式模型评测，不能将该速度作为本次实现的实测或端到端提速承诺。

## 修复边界

Hitch 的源码改动与测试在同名分支。完整数据集校验保留在准入/执行准备阶段；单题发布只能使用绑定到本次评测、候选、数据集和任务集合的校验凭据，重新验证清单、目录成员与当前题目内容。没有可信凭据的调用继续完整校验。不能通过调用者随意传入任务 ID 来降低校验范围。

Hitch 现在先等待所有发布生产者完成，再关闭发布队列；写入成功后才更新内存状态，失败会向上传递。异常/取消终结时保留已发布记录，结果与进度在同一把锁下同步。观察接口读取同一个结果/进度快照，并修复进程在两次写入之间崩溃留下的状态差异。旧的 running 投影不能覆盖终态；合法无效槽位补跑仍可更新证据。远程补跑重启恢复时，只有经过冻结请求、执行计划和派发记录校验的补跑，才能替换原无效槽位；普通恢复不能借此向终态追加结果。

校验凭据同时绑定评测、请求、候选、数据集、题目和 trial 目录。评分与 native descriptor 消费凭据前重新核对身份和清单元数据；descriptor 使用已经参与内容摘要的字节快照。原有硬链接数据文件继续支持，符号链接和扫描中内容变化会被拒绝。

准备阶段失败且尚无任何题目结果时，原有显式重试入口先将旧记录保存在 `reruns/<id>/previous-attempt/`，再移除当前旧终态投影、开始新尝试。再次失败仍写出新的失败结果；当前最终结果含题目记录或为取消状态时，该入口拒绝重启。

Gear 的 `inspectResult` 现在优先处理已持久化结果，并在分类失败前检查 schema 与 eval ID。最终结果仍经过原有候选身份、任务覆盖和评分证据校验；失败但含无效题的结果仍交给恢复流程。没有最终结果时，继续按 control 判断运行/失败/未知。

正式评分仍要求完整覆盖；正常 0 分不重跑。此修复不解封历史轮次、不延长冻结预算、不将尚未发布的底层结果自动计入正式证据。后续正式评测需使用包含 Hitch 修复的新构建与新的合法评测身份。
