# MLE-bench tasks

Import a declared task package with Hitch's MLE-bench importer, then use Gear's ordinary Harbor benchmark import and Hitch evaluation provider. Read the imported instruction, delivery contract and parameter policy before configuring the project. The initial example is `examples/mle-bench/harness/`; compose it with a generic Agent adapter that exposes normal terminal, file and code tools.

Resource datasets use the current manifest schema `3`. Gear verifies and derives their source identities through Hitch's public resources SDK, preserving resource locks and private-resource references. Install the matching Hitch build, or set `GEAR_HITCH_EXECUTABLE` to its executable when importing and running from a checkout. Old resource manifest versions are rejected. The selected Hitch resource store must retain the producer's resources; moving descriptor files alone does not transfer private data or images.

One Target slot executes the complete task, including analysis, training, prediction and delivery. Set repetitions explicitly. Baseline plus two candidates with two repetitions each consumes six full executions; local model comparisons within one sandbox do not create extra Target sessions. Use the project's existing ledger for retries and new evaluation versions. Do not reuse historical research projects or checkpoints; reimport a task and register a new budget.

Method parameters, such as internal CV, are separate from the formal evaluation. Read the package's exact JSON Pointer policy and submit only authorized Meta overrides with the candidate. Target choices use the task's documented action submission channel before training. Task-start values are frozen before Agent launch; replacing a parent object or local policy copy grants no extra rights. Generic resource budgets remain binding. Unsupported hard fit, trusted CV or selection-freeze requirements must fail admission before a model call.

For a DSH harness, the producer can declare `candidate_parameters` as `environment/candidate/gear-target/preset/task-parameters.json`. The candidate file contains `{"version":1,"tasks":{"TASK_ID":{"method":{"cv":{"folds":4}}}}}`; keys name task IDs and values are authorized partial parameter overrides. Gear injects this file with the ordinary candidate tree. Hitch remains the authority that accepts or rejects each value. Gear preserves the original evaluation inputs before adding the candidate, so candidate edits do not change the formal evaluation identity.

For scored tasks, configure the optimization objective from the independent verifier's declared quality metric. A delivery-only task has no external quality metric: file validity/pass rate is not accuracy. Internal CV and self-reported fit counts are diagnostic evidence unless explicitly verified. Missing or invalid quality evidence cannot justify quality-based promotion. Never merge private labels or hidden grading resources into the harness or Meta evidence.

Improve the prompts, optional workflow guidance, skills and ordinary tools that the Target actually loads. Inspect authorized trajectories, code, output artifacts and bounded errors through the existing Gear/Hitch APIs. Explain the observed gap, concrete change and expected result in the Meta generation summary. Do not add a mandatory research state machine, pipeline factory or separate final-refit operation.

Keep comparisons within the same task/evaluation identity. A permitted internal-method change can be compared through the common external grader. A change to private split, grader, metric or formal evaluation requires a new evaluation identity and baseline assessment within the registered budget. If allowed compute limits differ between candidates, record them and avoid claiming equal-compute comparison.
